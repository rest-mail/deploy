# rest-mail deploy

The chart that installs rest-mail into a Kubernetes cluster, as one release.

```sh
helm install rest-mail oci://ghcr.io/rest-mail/charts/rest-mail --version 0.4.0 \
  --namespace rest-mail -f my-values.yaml
```

It builds nothing itself. Each part of rest-mail is a chart in its own right,
published from the repository that builds it; this one pins which versions
belong together and configures them to work as one product.

| Subchart | From | Default |
|---|---|---|
| `server` | `oci://ghcr.io/rest-mail/charts/restmail` — rest-mail-server's `helm/restmail` | on, REST API only |

The website joins as a second subchart once it has a chart of its own.

## What the installer provides

Never generated by the chart, because some of it must outlive any release:
`MASTER_KEY` encrypts private keys at rest, so a value regenerated on upgrade
would leave every stored key unreadable.

| Secret | Keys |
|---|---|
| `restmail-api` | `JWT_SECRET` (32+ bytes), `MASTER_KEY` (16+ bytes) |
| `restmail-postgres` | `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` |
| `restmail-tls` | `kubernetes.io/tls` — e.g. a cert-manager Certificate |

Plus the cluster's own facts: `server.mailserver.hostname`/`domain` and the
`server.api.ingress.*` block.

## The mail gateways

SMTP, IMAP and POP3 start off: each wants a `LoadBalancer` on a privileged
port, and the phone and web clients speak only REST. Turn one on with
`server.smtpGateway.enabled=true` where the cluster can give it an address.

## Releasing

Bump `version` in `charts/rest-mail/Chart.yaml` and merge; CI publishes it and
refuses to overwrite a version already published. To move a part forward,
bump its dependency version and run `helm dependency update charts/rest-mail`
so `Chart.lock` follows.

Test locally with `charts/rest-mail/tests/render-test.sh`.
