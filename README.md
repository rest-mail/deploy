# rest-mail deploy

The chart that installs rest-mail into a Kubernetes cluster, as one release.

```sh
helm install rest-mail oci://ghcr.io/rest-mail/charts/rest-mail --version 0.7.0 \
  --namespace rest-mail -f my-values.yaml
```

It builds nothing itself. Each part of rest-mail is a chart in its own right,
published from the repository that builds it; this one pins which versions
belong together and configures them to work as one product. It also holds the
workflow those repositories build their images with (see
[Building an image](#building-an-image)).

| Subchart | From | Default |
|---|---|---|
| `server` | `oci://ghcr.io/rest-mail/charts/restmail` — rest-mail-server's `helm/restmail` | on: the REST API and the SMTP, IMAP and POP3 gateways |
| `website` | `oci://ghcr.io/rest-mail/charts/website` — rest-mail/website's `charts/website` | off: rest-mail.com itself |

## What the installer provides

Never generated by the chart, because some of it must outlive any release:
`MASTER_KEY` encrypts private keys at rest, so a value regenerated on upgrade
would leave every stored key unreadable.

| Secret | Keys |
|---|---|
| `restmail-api` | `JWT_SECRET` (32+ bytes), `MASTER_KEY` (16+ bytes), `BOOTSTRAP_ADMIN_PASSWORD` (16+ characters) |
| `restmail-postgres` | `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` |
| `restmail-tls` | `kubernetes.io/tls` — e.g. a cert-manager Certificate |

`BOOTSTRAP_ADMIN_PASSWORD` is the first admin's password, and without it nobody
can sign in. Whoever signs in with it must choose their own password and enroll
an authenticator at once, after which it stops working; it also expires 72
hours after it is first applied.

Plus the cluster's own facts: `server.mailserver.hostname`/`domain` and the
`server.api.ingress.*` block.

## The mail gateways

SMTP, IMAP and POP3 are on. They are how any ordinary mail client reads and
sends mail, and how other mail servers deliver to this one. Administration is
not among them: that is the rest-mail app and the admin webmail.

Mail clients connect over TLS only: 465 to send, 993 for IMAP, 995 for POP3.
There is no 587, 143 or 110. Port 25 is for other mail servers: it offers
STARTTLS, and takes mail from a server that will not use it.

Each gateway is a `LoadBalancer` Service on those ports. k3s gives them the
node's address out of the box; elsewhere the cluster needs a load balancer, or
the Service waits for an address forever. Without one, turn a gateway off with
`server.smtpGateway.enabled=false` (likewise `imapGateway`, `pop3Gateway`): the
REST API works without them.

Mail clients refuse a certificate they do not trust, so `restmail-tls` must
hold a publicly trusted one for the mail hostname.

## Releasing

Bump `version` in `charts/rest-mail/Chart.yaml` and merge; CI publishes it and
refuses to overwrite a version already published. To move a part forward,
bump its dependency version and run `helm dependency update charts/rest-mail`
so `Chart.lock` follows.

Test locally with `charts/rest-mail/tests/render-test.sh`.

## Building an image

`.github/workflows/image.yml` is the one build for every rest-mail container
image (`reference-postfix`, `reference-dovecot`, `reference-rspamd`), so
their versioning and publishing cannot drift apart. An image repository calls
it from its own `build.yml`:

```yaml
name: build

on:
  push:
    branches: [master]
    tags: ["v*"]
  pull_request:
  workflow_dispatch:

permissions: {}

jobs:
  image:
    # The most image.yml asks for. Its validate job narrows this to
    # contents: read; only its publish job, on a trusted run, uses packages.
    permissions:
      contents: read
      packages: write
    # The full 40-character sha of a commit on this repository's main, never a
    # branch or tag that could move under the caller.
    uses: rest-mail/deploy/.github/workflows/image.yml@<commit sha on main>
```

The same three lines of `jobs:` serve `reference-postfix`, `reference-dovecot`
and `reference-rspamd`: each builds the `Dockerfile` at its root for
`linux/amd64,linux/arm64`, the defaults. Pin the sha of the merged commit that
added the workflow, and move it forward as a reviewed change of its own;
a comment after the sha naming the rest-mail/deploy pull request says what it is.

What a run does:

| Run | Builds and checks | Publishes to `ghcr.io/<owner>/<repo>` |
|---|---|---|
| push of tag `v1.2.3` (or `v1.2.3-rc.1`) | yes | `1.2.3` — a version, what anything deploying it pins |
| push to the default branch | yes | `latest` and the commit's short sha — for trying a change, never pinned |
| pull request (forks too), other branch, any other event | yes | nothing: no login, no token beyond reading the code |

Images are versioned with SemVer only. A tag that is not `vMAJOR.MINOR.PATCH`
fails the run, and so does one shaped like a date (`v2026.10.18`): there are
no CalVer tags, and none should be made again. The destination is always the
calling repository's own package; no input can point it anywhere else.

By default, nothing is pushed unless the image declares a `HEALTHCHECK` (not `NONE`),
checked on the image built in the same job, just before it logs in. That is
the image saying how to tell it is healthy, not proof that the service starts:
Postfix, Dovecot and rspamd each need their own configuration to come up. A
repository that has a fixture for that passes it as `runtime-check`, an
executable in the repository run with `IMAGE` set to the built image; a
failing one stops the publish.

One-shot jobs such as `reference-certgen` may set `require-healthcheck: false`
and provide a `runtime-check` that runs the job, requires a successful exit,
and validates its output. The exemption skips only the image's HEALTHCHECK
declaration check in both jobs; runtime validation still runs. Do not add a
placeholder HEALTHCHECK to an image that exits after completing its work.

| Input | Default | |
|---|---|---|
| `context` | `.` | build context, inside the repository |
| `dockerfile` | `<context>/Dockerfile` | |
| `platforms` | `linux/amd64,linux/arm64` | the first is the one checked |
| `runtime-check` | none | e.g. `tests/health.sh` |
| `require-healthcheck` | `true` | `false` exempts one-shot jobs from the image HEALTHCHECK requirement |
| `publish` | `true` | `false` keeps a run to validation; it never lets one publish that otherwise could not |

Test it locally with `tests/image-workflow/test.sh` (`REAL_DOCKER=1` also
builds the HEALTHCHECK fixtures, one platform, `FROM scratch`). CI runs that
and calls the workflow on `tests/image-workflow/fixtures/healthy` for every
platform, with `publish: false`, plus the no-healthcheck fixture with the explicit
one-shot exemption.
